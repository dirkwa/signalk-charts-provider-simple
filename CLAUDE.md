# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Per project convention: `npm run format` → `npm run build` → `npm run test`.

- `npm run build` — `vite build` to `dist/` (`vite.config.ts`), one output file per source module so the worker processes and threads, the catalog CLIs and the tests can load single modules; dependencies stay external. `vite-plugin-checker` runs `tsc` inside the build and fails it on the first type error, and `vite-plugin-dts` writes the `.d.ts` files. Then `build:public` compiles the webapp scripts with `tsc`.
- `npm run build:watch` — `vite build --watch`
- `npm run test` — runs `pretest` (build + `build:tests` + regenerate `test/fixtures/test-chart.mbtiles`), then `node --test --test-force-exit dist-test/**/*.test.js`
- Run a single test file: `npm run build && npm run build:tests && node --test --test-force-exit dist-test/<name>.test.js`
- Run a single test by name: append `--test-name-pattern "<regex>"` to the node command
- `npm run lint` / `npm run lint:fix` — ESLint (typescript-eslint `strictTypeChecked` over `src`, `test`, `e2e`, `public/js`, `playwright.config.ts`)
- `npm run format` — Prettier on `**/*.ts` under `src`, `test`, `e2e`, and `public/js` (plus `playwright.config.ts`), then `eslint --fix`
- `npm run format:check` — non-mutating CI check

Node ≥ 22.5 is required: the plugin reads MBTiles via the built-in `node:sqlite` module (no native compile). The `pretest` step regenerates the MBTiles test fixture; if a test reports "fixture missing", run `npm run test:fixtures`. The fixture scripts are TypeScript run directly by Node, which needs Node 22.18 or later for development (type stripping); the plugin itself still runs on 22.5.

## Architecture

This is a Signal K server plugin. The single entry is `src/index.ts`, which exports a `pluginConstructor(app)` factory returning the `Plugin` object Signal K calls (`start` / `stop` / `schema` / `registerWithRouter`). Built output lands in `dist/` and is what npm publishes alongside `assets/`, `public/`, and `docs/screenshots/`.

### Two responsibilities, one plugin

1. **Serve charts to Signal K** (display path).
   - `charts-loader.ts` walks the configured `chartPath` recursively and produces a `Record<string, ChartProvider>` keyed by identifier. It handles `.mbtiles` files, `.pmtiles` archives (`utils/pmtiles-reader.ts`, read by byte range with tiles served as stored), tilemap directories (with `tilemapresource.xml`), and online charts (`.onlinechart.json`, see below).
   - **Online charts** (`utils/online-charts.ts`): an online chart added from the Online Charts or Satellite tab is a small `<catalogId>.onlinechart.json` file in the chart folder holding its catalog id and display name, and optionally a `defaultOpacity` that overrides the catalog entry's. Being a file, it gets folders, enable/disable, move and delete for free. It is served (as `_fileFormat: 'online'`, no local tiles) only while the downloaded catalog lists its id, so catalog fixes reach every boat. In any code path that can receive either file kind, derive a chart's id from its file name with `chartIdFromFilename`. A chart's id is its file stem and is shared across the whole library, so new online chart files take an id no other chart uses. Online charts are served on the v2 API only.
   - **Masked versions** ("Water only" and "Land only"; the file's `mask: 'water-only' | 'land-only'`, named for what is kept): a kept online chart can be added again as its own `.onlinechart.json` with the land or the water cut away, sharing the chart's tile store. "Water only" fails open (the plain tile); "Land only" lies on top of the other charts, so it fails closed (a transparent tile, never the raw one), shrinks the land a little before the fill so a chart's shoreline shows, starts below full opacity, and is added only once its warning is acknowledged. `utils/masked-tiles.ts` masks a tile the first time it is served, from the proxy's unmodified tile, through the raster worker pool (`raster-mask.ts`, pure-JS scanline fill in `land-geometry.ts`), and keeps the result in the masked instance of `raster-tile-cache.ts`, keyed by chart, mask and land index version and stamped with the source tile's `fetched_at`. The OSM land polygons live in a SQLite R-tree index (`land-index.ts`), built by a worker (`land-index-worker.ts`) that streams the zips with `unzipper`; `land-index-manager.ts` owns its state and builds only after the user agreed to the download. Masked versions are not served (left out of the chart list, tiles 404) until the index is built.
   - **Time-varying online charts** (weather radar, satellite, forecasts): `utils/time-poller.ts` reads each served entry's GetCapabilities at its `refreshInterval` — one poll per catalog entry, only while a client is reading the chart (resource reads call `touch`), with one download per capabilities URL — and `utils/time-dimension.ts` turns the layer's TIME dimension into the chart resource's `time` block (Plotter Extensions `charts.time` convention), clamped to the entry's `window`. The update is applied to the served chart in place and emitted as a delta that differs only in `time`, which plotters absorb without reloading; keep everything else in the served chart stable between polls. The dimension is found with a targeted text scan, not a full XML parse, because some capabilities documents are megabytes.
   - **Metered and offline links** (`utils/internet-state.ts`): `InternetGate` follows signalk-internet's `network.internet.state` through one subscription from the plugin's start to its stop; the server sends the last value when the subscription starts. On `metered`, `offline` or `captive` nothing starts on its own (catalog and ENC index checks, a resumed land index build), and the tile proxy and time poller serve kept data only; `allowMeteredChartDownloads` lets chart tiles through on `metered`. What the user starts always runs. Background work waits for a state only while signalk-internet is enabled and has published none, after a start and after the `null` it publishes when it stops, bounded by `FIRST_STATE_WAIT_MS`; the plugin list is asked only then. A published state is believed as it is: signalk-internet after 0.7.1 clears it with `null` when disabled. Without signalk-internet, keep behaviour exactly as it would be without the gate: no waits, timers or UI.
   - `utils/mbtiles-reader.ts` opens MBTiles via `node:sqlite`. `utils/mbtiles-metadata.ts` reads/writes the `metadata` table (used for chart rename, which marks tiles "USER MODIFIED").
   - **Missing raster tiles** (`utils/raster-overzoom.ts`): a jpg/png MBTiles tile missing inside the zoom range is synthesized in worker threads from the nearest stored ancestor and the stored children. Synthesis is slow on a Raspberry Pi, so results sit in a small per-reader LRU and on disk under `<dataDir>/raster-tile-cache/`, which survives restarts. `utils/raster-tile-cache.ts` documents the cache key, size cap, eviction and pruning. Chart files and the chart folder are never written.
   - `ChartProvider` exposes both `v1` and `v2` shapes (see `src/types.ts`) so the plugin works on Signal K v1 and v2 servers; `serverMajorVersion` is sniffed from `app.config.version`.
   - **Shared ENC store** (`utils/enc-store.ts`, `docs/enc-store.md`): S-57 cells as delivered, for other plugins (signalk-underkeel) to read in place, one collection per chart set (always, by hard link) or converted chart (with `keepEncCells`). A collection belongs to one owner and only its owner replaces it. A cell is renamed into place whole, an unchanged cell keeps its files and modification times, and listeners hear of a collection once its write is done. Peer plugins use `globalThis.__signalk_chartsProviderEnc`, other clients `/enc-store`; keep the layout and the API additive.
   - `utils/chart-state.ts` persists per-chart enable/disable in the plugin data dir; `utils/folder-state.ts` does the same per folder (a disabled folder hides all descendant folders' charts; effective visibility is chart-enabled AND folder-path-enabled); `utils/file-scanner.ts` enumerates folders for the management UI.

2. **Convert charts on demand** (write path; see `docs/chart-conversion.md` and the *Conversion runtime* section below). Two toolchains: the **container** one (GDAL + tippecanoe + tile-join in the charts-toolbox image via the `signalk-container` plugin, preferred) and the **WebAssembly** one (gdal3.js + the built-in tiler, in-process, the fallback). `utils/conversion-backend.ts` picks one per conversion before anything is written (`chooseConversionBackend`: runtime detected, image present or pullable, every mount path resolvable; else WebAssembly, with `fallbackNote` in the log); the `conversionEngine` config (`auto` / `container` / `wasm`) pins one, and pinned to `container` a conversion it cannot run fails instead of falling back. The converters own progress, naming and metadata patches, and hand each toolchain a `ConversionReport`; never call one toolchain's module from the other.
   - `utils/s57-container.ts` / `utils/rnc-container.ts` are the container toolchain: the GDAL export script, per-band tippecanoe + tile-join (single-bucket bundles run one tippecanoe), basemap rasterize/translate/`gdaladdo`, and BSB `gdal_translate` + `gdaladdo`. S-57 cells (with their update files, `cellFiles` in `utils/s57-export-files.ts`) are staged into the conversion's scratch dir before the export, so the job sees exactly the selected cells. Helper-job labels are `<stage>-<chartNumber>`, which orphan reaping in `index.ts` parses.
   - `utils/gdal-wasm.ts` drives GDAL compiled to WebAssembly (`gdal3.js`) through its C API, mounting host directories with NODEFS. It runs only inside the conversion workers.
   - `utils/worker-pool.ts` + `utils/conversion-process.ts` + `utils/conversion-worker.ts`: each conversion opens a pool of workers and runs typed tasks on it — a GDAL utility, one S-57 cell's export, a tiling step, a raster overview tile. Each worker is a child process (`fork`, `MALLOC_ARENA_MAX=2`, its heap limit on the command line) running the task on a thread of its own, so its main thread relays tile batches while a shard is tiled. Not worker threads in the server: their WASM heaps and malloc arenas stayed resident after the pool closed; a process returns them when it exits. Aborting the pool's signal kills the workers, which is how a conversion is cancelled mid-stage.
   - `utils/s57-converter.ts` runs S-57 ENC and the SHP basemaps on the chosen toolchain (WebAssembly: GDAL export per cell → vector tiler; rasterize → MBTiles → overviews). `planTileSources` turns the GDAL export into one tiler source per layer and IHO band, each at its band's zooms (`utils/s57-band.ts`), so a whole bundle is tiled in one pass. Both toolchains start a feature with an S-57 `SCAMIN` at the zoom S-52 shows it at (`utils/s57-scamin.ts`, capped at the band's maxzoom): the container one as `tippecanoe.minzoom`, the WebAssembly one through `ShardGroup.scamin` in the tiler. `processS57Directory` is the reusable core (convert an already-extracted ENC tree); `processS57Zip` is a thin wrapper that extracts one ZIP then delegates to it.
   - `utils/vector-tiler.ts` (main thread) + `utils/vector-tile-shard.ts` (workers) are the replacement for tippecanoe/tile-join: bucket features into shards on disk, tile each shard with geojson-vt + vt-pbf, merge tiles that shards of different minzooms both produce. Keep geometry exact (no simplification, no feature or size limits).
   - `utils/rnc-converter.ts` converts BSB/KAP raster (`processRncZip`) and Pilot tarballs (`processPilotTar`) on the chosen toolchain; on WebAssembly, GDAL's translate API writes a PNG MBTiles at the chart's native zoom, then `utils/raster-pyramid.ts` adds overview zooms (the `gdaladdo` replacement). `utils/tar-extract.ts` reads `.tar` / `.tar.gz` / `.tar.xz` in JavaScript.
   - **Charts already on the server** (`utils/local-chart-source.ts`, `POST /convert-local`): the Convert tab converts a folder or ZIP on the server's disk as well as an upload. The folder is searched for S-57 cells or BSB charts, loose or in ZIP files; it is only read, and its ZIP files are extracted into a new `convert-local-…` work folder (`mkdtemp`) in the data dir, which `utils/temp-dirs.ts`'s sweep of leftover work folders, run only at a process's first start, leaves alone when a config save restarts the plugin mid-conversion. `processS57Local` / `processRncLocal` convert what it holds; the S-57 pipeline keeps one cell of each name (`uniqueCells`), since two copies would write the same GeoJSON. BSB charts in a folder the helper container cannot mount fall back to WebAssembly. Every conversion route refuses a chart number already converting or about to (a catalog download): `isConversionNameInUse`, since the converting state is keyed by it.
   - `utils/concurrency.ts` is the **single source of truth for CPU usage**: the plugin config's `cpuBudget` is applied with `setCpuBudget` in `start()`, and `getCpuBudget()` returns the live budget for both toolchains (its fields are defined there), so converters pick up changes between jobs without a restart. Don't reimplement CPU/concurrency logic elsewhere — read it from this module.
   - `utils/catalog-manager.ts` downloads and caches the merged chart catalog from this repo's GitHub Pages (see *Merged chart catalog* below; `CHARTS_CATALOG_URL` overrides the URL for development against a fork) and tracks installed catalog charts so update notifications can fire.
   - `utils/download-manager.ts` is a queue with progress for direct-URL downloads and ZIP extraction.
   - **ENC Charts** (the `ENC Charts` tab; UI calls each bundle a "chart set"): the tab draws the units of the ENC index (see *Merged chart catalog* below), and one set can mix units from any source. `utils/enc-index-manager.ts` downloads and caches `enc-index.json` the way the catalog manager handles the catalog (ETag, last good copy on disk, `ENC_INDEX_URL` overrides the URL); only chart sets need it, never chart serving. `utils/enc-chart-set.ts` is pure: it turns a set's selection into the cells to download, including updates a source publishes in separate archives. `utils/custom-catalog-manager.ts` persists each set as JSON under `<dataDir>/custom-catalogs/` (safe-slug ids, path-traversal-checked), migrates sets saved by the old NOAA Charts tab, and evaluates freshness by comparing each cell's index version with the snapshot taken at download. NOAA units stay in `selectedBand4ChartIds` and other units go in `selectedUnitIds`, so an older plugin still opens a set and shows its NOAA part; keep schema changes to these files additive. `utils/custom-catalog-download.ts` downloads each archive once (paced per host, with the index build's TLS and header fallbacks), extracts only the selected cells into one combined tree (zip-slip-safe), and numbers separately published updates on so GDAL applies them. `utils/chart-set-cache.ts` keeps each set's cells between runs under `<dataDir>/chart-set-cache/<setId>/` (the raw cell, its GDAL GeoJSON gzipped, and the version and export revision), so an update downloads and runs GDAL only on cells whose version changed; bump `CELL_EXPORT_REVISION` when the GDAL export changes what it writes. A cell is renamed into place only once complete. The `/custom-catalogs*` routes in `index.ts` drive download → per-cell GDAL export into the cache → `processS57Directory` over the cached cells (its `geojsonFor` hook supplies the kept GeoJSON in place of GDAL) → quarantine promote, producing one MBTiles per chart set, named after the set. Server-side modules/routes keep the generic `custom-catalog` names.

### Merged chart catalog (`src/catalog/`, `catalog/`)

The Chart Catalog is backed by one merged catalog file that this repo publishes to GitHub Pages (see `docs/chart-catalog.md` for the why). It combines chartcatalogs.github.io (downloadable charts) with the curated online charts in `catalog/online-charts.json`, plus the per-file facets (label, category, format, regions, bbox) in `catalog/chartcatalogs-index.json`.

- `src/catalog/merged-catalog-schema.ts` holds the merged catalog's schemas: strict ones for the hand-edited sources, tolerant ones for the published file. The ENC index keeps its own in `enc-index-schema.ts` (published) and `enc-direct-sources.ts` (the hand-edited direct-source list). Published-file compatibility policy: additive changes keep `schemaVersion`; consumers ignore unknown fields and skip entries they can't interpret, never the whole file.
- `src/catalog/build-merged-catalog.ts` is pure (no I/O): merge, content hash, carry-forward of broken upstream files, the drop guard and the publish decision. `src/catalog/publish-catalog-cli.ts` is the I/O shell that `.github/workflows/publish-catalog.yml` runs; `src/catalog/preview-catalog-cli.ts` (`npm run catalog:preview`) runs it on each request to serve a contributor's working copy locally. Both are excluded from the npm package.
- `src/catalog/chartcatalogs-xml.ts` is the only chartcatalogs XML parser; the catalog manager and the build both use it.
- The content hash deliberately ignores timestamps and the upstream commit, so hourly chartcatalogs header-only commits don't republish.
- **ENC index** (`docs/enc-index.md`): `enc-index.json`, published beside the catalog by the same workflow job (a Pages deployment replaces the whole site), lists every free ENC as selectable map units. `src/catalog/enc-index-schema.ts` is its schema, `enc-outline.ts` the fixed outline simplification, `build-enc-index.ts` the pure assembly (reuse by archive version, carry-forward, drop guard), and `enc-index-cli.ts` the I/O shell (downloads, GDAL through the plugin's own worker pool and gdal3.js, so CI needs no container runtime). The published index is the build's state between runs. NOAA unit ids and versions are NOAA's own chart ids and `enc_ed_up` tokens, so saved NOAA chart sets map onto it by name; every other cell gets a version token of the same form from its DSID. A cell several sources publish appears once: a direct source's copy first, then EuRIS's (`PREFERRED_SOURCE`). Besides NOAA and chartcatalogs, the builder reads producers' own catalogs listed in `catalog/enc-direct-sources.json`, through one adapter per catalog format in `enc-direct-sources.ts`; they go into the ENC index only. Bump `ARCHIVE_REVISION` when a change gives different units for the same archive.

### Conversion runtime

- `gdal3.js` is pinned to an exact version in `package.json`, and the charts-toolbox image to a `:VERSION` tag in `utils/container-images.ts`. `backendBuildId()` (the image name, or `gdalBuildId()`, the gdal3.js version) keys the chart-set cache's per-cell GeoJSON, so bumping either, or a set's toolchain changing, makes chart sets re-export their cells once. A chart set's run picks its toolchain once and passes it (`options.backend`) to both its export and its tiling.
- gdal3.js exports only part of GDAL's C API (no `GDALBuildOverviews`, no progress callbacks); check `Module._<name>` exists before relying on a function.
- GDAL work and tiling never run on the server's event loop: add new heavy work as a `conversion-worker.ts` task, and as a helper job in the container toolchain.

### `signalk-container` integration

Every container-runtime call (image pulls, helper-job execution, mount resolution, orphan cleanup) goes through the `signalk-container` plugin, never `dockerode`. `utils/container-manager.ts` is a thin shim:

- Defines a local `ContainerManagerApi` type that is a **subset** of `signalk-container`'s published API — only the methods chart-provider calls (`runJob`, `resolveSignalkDataMount`, `resolveHostPath`, `cleanupOrphanedJobs`, `getRuntime`, `pullImage`, `imageExists`, plus the optional `whenReady`). We don't `import` from `signalk-container` because it's a peer plugin (loaded by Signal K, not bundled), so the shim is the API contract we depend on.
- `waitForContainerManager()` discovers the manager on `(globalThis as any).__signalk_containerManager`. Plugin load order is non-deterministic, so it polls up to 30 s. `start()` runs it in the background (conversion never needs it); `settledContainerManager()` waits for a discovery still running and takes up a manager published later.
  - **signalk-container >= 1.6.0**: uses `manager.whenReady()` — a single await that resolves when runtime detection has settled.
  - **signalk-container < 1.6.0**: falls back to the original `while (!getRuntime()) await sleep` loop. The `whenReady?():` declaration is intentionally optional so older versions keep working.
  - Contract: `waitForContainerManager()` never rejects. `whenReady()` rejections are swallowed and treated as "detection didn't settle in time".
- Orphaned helper jobs are reaped once per process, and only before this process ran a job (`hasStartedJobs` in `utils/container-jobs.ts`): a config save restarts the plugin while its conversions keep running.

If `signalk-container` is missing, nothing is an error: charts convert with WebAssembly and the Convert tab says so.

### Hot-apply config and the path marker

`start()` is called fresh on every config save (Signal K restarts the plugin, not the whole server). Downloads and conversions the previous start began keep running, so the leftover work folders in the data dir are swept only at a process's first start (`utils/temp-dirs.ts`). The startup sweep of the chart folder (invalid `.mbtiles`, orphaned journal and WAL files) waits a while after the charts load, so a run of config saves does not reopen every chart each time, and it never deletes a chart that an upload or conversion places or replaces while it runs. `utils/path-marker.ts` writes `.charts-provider-marker.json` into the chart path on each start, recording plugin version, container hints, and effective UID — useful when diagnosing host-vs-container path mismatches.

### Web UI

`public/` is a static webapp served by Signal K at `/plugins/signalk-charts-provider-simple/`. It talks to Express routes registered in `index.ts` via `registerWithRouter`. The UI has seven tabs: Manage Charts / Download from URL / Convert / Chart Catalog / Online Charts / Satellite / ENC Charts. The merged catalog's downloadable charts are in Chart Catalog (`public/js/chart-catalog.ts`); its online charts are in Online Charts, except those of category `imagery`, which the Satellite tab lists. Both are an `OnlineChartPanel` in `public/js/online-charts.ts`, which also holds the add-by-URL form; all three read `/catalog-registry`. Scripts are plain `<script>` tags (no bundler); cross-file references go through `window.X`. The ENC Charts tab (`public/js/enc-charts.ts`) uses Leaflet, vendored under `public/vendor/leaflet/` so the map UI loads offline (only basemap tiles need a network); `@types/leaflet` types the global `L` for the strict `public/js` build.

### Type extensions

`@signalk/server-api`'s `ServerAPI` type is missing `app.config` and Express route helpers that the real server provides; `src/types.ts` defines `ExtendedServerAPI` for those. When adding new server-API uses, extend that interface rather than casting.

### Tests

Plain Node test runner against compiled output in `dist-test/**/*.test.js`. Test sources are TypeScript (`test/**/*.ts`) compiled via `tsconfig.test.json`; `pretest` runs `build`, `build:tests`, and `test:fixtures` in that order. `test/integration.test.ts` exercises the loader against `test/fixtures/test-chart.mbtiles` (regenerated by `test/fixtures/create-test-mbtiles.ts`, run directly by Node's type stripping).

## Releases

release-please cuts releases; never bump `package.json`'s version by hand. Squash-merge PRs with a Conventional Commit title: `feat` gives a minor release, `fix`/`perf`/`revert`/`build(deps)` a patch, and `!` or a `BREAKING CHANGE:` footer a major one. release-please keeps a `chore(release): X.Y.Z` PR open, and merging it tags the release, creates the GitHub Release and dispatches `publish.yml`. `.github/workflows/label-by-title.yml` labels each PR from its title, and `.github/release.yml` groups the release notes by those labels. A `-beta.N` pre-release is still tagged by hand: bump `package.json` on a branch, then push the tag.

## Code conventions

- TypeScript strict mode + `strictTypeChecked` lints. `eqeqeq`, `curly: all`, `no-var`, `prefer-const` are enforced; `no-console` is intentionally off (the plugin logs through `console`).
- Prettier is wired through ESLint, so `prettier/prettier` violations fail lint.
- Schemas use the unscoped `typebox` package (1.x), not `@sinclair/typebox`, which stopped at 0.34. TypeBox 1 was published under a new name rather than a major bump, so `npm outdated` never points at it. Validation errors carry `instancePath`, and a self-referencing schema is a `Type.Cyclic` with `Type.Ref`.
